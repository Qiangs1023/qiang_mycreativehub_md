# 指令越写越多时，我宁可先删掉打架的规则

昨天刷到一个很小的工具，叫 Clogmeter，刚在 Product Hunt 上线。它做的事很简单：把 `AGENTS.md`、`CLAUDE.md`、Cursor 规则和技能文件称一称，看每段话要花多少 token，有没有重复，有没有「永远要」和「永远不要」在打架。

我第一反应不是「又多了一个该装的工具」，而是有点不自在——自己这边的指令，是不是也在悄悄变厚。

越用 Agent，越容易靠加规则来获得安全感。出过错，就补一条；担心它越权，再补一条。过一段时间，文件看起来很负责，Agent 却开始犹豫。

我想清楚的是：控制感并不来自规则的数量。互相打架的指令，比指令太少更麻烦。

---

## 指令变厚，往往不是一天发生的

2026 年 11 月 10 日，Clogmeter 在 Product Hunt 上线。它的[介绍](https://dev.to/clogmeter/clogmeter-is-live-on-product-hunt-see-what-your-agent-instruction-files-cost-4od9)写得很直白：如果你用 Claude Code、Cursor 或 Codex，Agent 每一轮都会重读那些指令文件。文件会自己长大，规则会被复制到好几处，迟早冒出互相矛盾的句子。比如一处写「永远要跑完整测试」，另一处写「永远不要跑慢测试」。模型两边都付钱，然后开始对冲。

工具本身很克制。[网页版](https://clogmeter.vercel.app/)可以粘贴或拖入文件，统计每个文件、每个章节的 token，标出近似重复，标出 always/never 冲突，并建议先删什么。分析在浏览器里完成，文件不会被上传。他们给的示例里，一份 720 token 的 `AGENTS.md`，已经能抓到近乎重复的 PR 审查清单，以及「永远 force-push 到 main」和「永远不要在推 main 时用 `--force`」这种正面对撞。

11 月 2 日，他们还写过一篇更短的判断：[先砍掉一条互相冲突的规则，再谈别的删减](https://clogmeter.vercel.app/posts/cut-conflicting-rules-first.html)。这句话比「把文件缩到多短」更对我的胃口。重复会浪费上下文；冲突会让模型学会骑墙。

这不是一个新问题，只是终于有人把它称出来了。Anthropic 在 [Claude Code 文档](https://code.claude.com/docs/en/claude-md)里写得很明确：每个 `CLAUDE.md` 最好控制在 200 行以内，更长的文件会占掉更多上下文，也会降低遵守度。这些文件被当成上下文，而不是强制配置。真的不能做错的事，应该放到 hook 里，而不是指望一句「千万不要」永远生效。他们也提醒：两条指令互相矛盾时，Claude 可能任意选一条。

我看完这些，没有急着给数字旷野再加一套「指令审计技能」。我想先问自己：现在这些写作和发布相关的规则，是不是已经多到开始互相挡路了。

## 我真正担心的，不是 token，是判断被稀释

token 当然有成本。指令每轮都要重读，文件越厚，每一次对话都更贵，也更容易在长会话里被压缩掉。但对我来说，更烦的是另一种损耗：规则一多，Agent 开始变得「都对，又都不敢」。

数字旷野这条写作流水线，已经有选题、成稿、封面、同步备份这些步骤，也有很硬的界限——草稿默认是 `draft`，不能自己推 main，也不能在我没点头的时候把稿子变成已发布。这些界限是必要的。

必要，和「再多写一遍」不是一回事。

同一条发布门禁，如果在技能文件、例行说明、聊天提示里各写一遍，还微微不一致，Agent 不会因此更听话。它更可能在该停的地方犹豫，在不该发挥的地方自由发挥。写作里也有同类对撞：一处习惯了「每天都要交一篇完整稿」，另一处又写「没有好选题就不要硬凑」。这两句要是同时出现在常驻指令里，执行的人就得猜今天该勤奋，还是该克制。

加规则的心理也很熟悉。哪天稿子里出现一句不像自己的话，就想再补一条语气禁令；哪天出处没核对到，就想再写一段「绝不编造」的强调。禁令可以写，可如果只是把焦虑翻译成更长的 always/never，文件会越来越像一份吓自己的清单。

Anthropic 也说了，在 `CLAUDE.md` 里加 IMPORTANT，往往解决不了「它怎么还是没听」。要么文件已经太长，那一行被淹没了；要么这件事根本不该靠散文约束，而该放到真正会拦住它的机制里。

所以我的判断变得很简单：指令文件也该像文章一样可复查。我要能一眼看到现在到底有哪些硬规则，它们是不是还一致，而不是靠不断追加来维持安全感。

---

## 所以我给自己定了三条很短的做法

第一，先称，再加。再往技能或总指令里塞新规则之前，先看现有文件里是不是已经有一句意思接近的话，或者已经有一句和它打架。Clogmeter 这类工具可以用，Anthropic 自己的 `/doctor` 和提示词审计也可以用。没称过就先加，多半只是在叠床架屋。

第二，常驻的指令保持很薄，流程放到按需加载的技能里。身份、硬界限、以及「稿子默认是草稿、发布权在人这边」，适合常驻；封面怎么填变量、样稿怎么同步备份，适合写在被点到才加载的工作流里。地图放在根文件，路程写在技能里。

第三，真正不能错的事，不要只写在 Markdown 里。禁止推 main、禁止把 `status` 改成 `published`、禁止在未确认时触发上线，这些应该是权限和流程上的硬挡板，而不只是一句「千万不要」。散文里的 never，被忽略一次就可能来不及收回。

至于 Clogmeter，我会把它当成一把秤，而不是又一个要每天打开的仪表盘。哪天指令又开始发胀，就称一次，先删打架的，再删重复的，最后才考虑要不要新写一条。

独立工作里，工具变强之后，最容易犯的错不是做得太少，而是把「更完整的控制」理解成「更长的说明书」。说明书可以帮我减少重复劳动；它不能代替我定期打开那些文件，看一眼自己到底在要求什么。

规则少而一致，Agent 反而更好用。这和写文章是同一件事：不是写得越多越清楚，而是把互相打架的句子先拿掉。
