这两天刷到 Julius Brussee 的 [Caveman Code](https://caveman.so/news/introducing-caveman-code)，第一眼很容易当成一个段子产品。它最出名的出身，是一份让 Claude 像洞穴人一样说话的 Markdown：「Why use many token when few do trick。」

笑话很有效。仓库冲到了约十二万星，Julius 也因此把这件事做成了全职工作。可我读完他 11 月 13 日前后的[发布说明](https://www.ycombinator.com/launches/XQG-caveman-f26-the-joke-with-120k-github-stars-is-now-the-most-efficient-coding-agent)之后，留下来的不是「少说话真省钱」，而是另一句更冷静的话：**Caveman 不只是让模型少说，更是让它少读。**

我的判断也很简单。Agent 的账单变贵，往往不是因为它今天格外啰嗦，而是我们把太多不必再看的东西，又一次塞回了它的上下文。

## 笑话打中的，只是账单里很小的一块

故事本身很好懂。大约七个月前，还在上学的 Julius 发现自己的 AI 账单已经高过菜钱。他写了那一份洞穴人风格的指令，本意近乎开玩笑。有人把它发到了 Hacker News，冲到首页，[仓库](https://github.com/JuliusBrussee/caveman)随后变成他的全职项目。

少说话当然有用，尤其在聊天式的来回里。可当模型开始真正「办事」——一轮一轮调工具、把结果读回来、再决定下一步——这套笑话就不够用了。Julius 在 Launch YC 里写得很直接：用 Claude Opus 5.5 量过之后，模型说出来的那些话，占不到成本的十分之一。大头在 harness，也就是提示词、工具，以及围在模型外面的那圈循环。是它决定了，每一轮请求里，模型不得不把多少旧东西再读一遍。

官方[长文](https://caveman.so/news/introducing-caveman-code)把这笔账拆得更清楚。在 Claude Opus 5.5、高推理强度的设置下，输出占账单的 43%，而输出里又有 78% 是推理过程；笑话要打掉的「说话」，确实不到十分之一。重新读一遍对话，占 32%；往对话里追加新内容，占 25%。

两件事从此变得很具体。

一件是：越早塞进去的东西，后面每一轮都要再付一遍。所以第一轮看起来只是「多贴了一点材料」，后面会放大成整段会话的固定成本。他们给的对比是：开始干活之前，Claude Code 的首轮请求大约 16.7k token，Caveman 在同一模型上是 2.7k；Codex 大约 11.8k，Caveman 在对应模型上是 3.4k。

另一件是：一份很肥的工具结果会付两次钱。一次是它进入对话的时候，一次是之后每次把整段对话再送回去的时候。Julius 的做法是让工具结果先留在程序里：模型写一段短程序去调用工具、留下它真正需要的结论，再把结论带回来。原始输出不进对话。他们说，仅这一处改动，就把一个连接外部应用的任务从 0.380 美元降到 0.127 美元。

一天跑下来，差距会被放大。同一模型上，他们自己在 2026 年 11 月、按标价、不经过路由的测量里，三个跨应用的全天会话，Claude Code 每次大约 7.65 美元、21.6M token，Caveman 是 1.83 美元、3.7M token，便宜 76%，token 少 83%。这是作者自己的评测，不是第三方复现，我把它当成一份很清楚的方向证明，而不是一句可以原样引用的行业结论。

## 省钱，不该先饿着它的推理

更让我停下来的，是他们决定不发布的那一步。

既然输出里大部分是推理，最容易想到的省法，就是把模型先前的推理从历史里丢掉，免得下一轮再读一遍。他们做过这个实验：重新阅读的成本降了 68%。可一次尝试的费用反而高了 19%，解出的任务少了 12.5 个百分点——因为模型每一轮都要花更多推理，把被拿掉的过程重新补回来。

所以他们没有上线。官方写的原则也很干净：**harness 应该靠拿掉机械步骤来少推理，而不是靠饿着模型来少推理；判断标准该是「做对一件事花多少钱」，而不是「一共少用了多少 token」。**

这句话比洞穴人梗更对我的胃口。独立工作里，我自己也容易把「省」理解成「砍」。上下文太长了，就想先删思考、再压缩解释、再把日志整段丢进去碰运气。看起来是在控制成本，其实是把必须发生的判断，从看得见的地方挪到了下一轮更贵的猜测里。

Caveman 把同一件事用在了人要看的地方。每个 pull request 先给一份短指南：一行摘要，以及「真正需要你做的那一个决定」，然后再把每处改动写成之前、之后、以及为什么。这和少读是同一条线。模型不该把整段工具垃圾再读一遍，人也不该把一百处细节先吞下去，才找到那一个真正要自己点头的位置。

## 所以我给自己留的，是更窄的入口

我不会因为这篇发布，就立刻把日常工具都换成 Caveman。产品还新，数字是作者自测，值不值得换，要看自己的工作是不是真的已经被「重读」拖贵了。但我愿意先改自己这边的习惯。

第一，开头少倒材料。资料、日志、整页网页、昨天的长讨论，不必在第一轮全部贴进去。先给任务、约束，以及「现在真正要用的那一小段」。需要时再取，比一开始就为整段会话买下一笔固定租金要便宜，也更不容易把判断淹没。

第二，工具的原始输出，尽量不要直接成为下一轮的正文。跑完测试、抓完网页、列出文件之后，留下结论、失败原因和可核对的位置就够了。整份日志可以放在旁边备查，不必默认成为对话的一部分。付两次钱的，往往不是那句结论，而是那坨以后再也不会被认真看的原文。

第三，不靠饿着推理来换安心。该想清楚的步骤，让它想；真正该减的，是重复搬运。少用了多少 token，不是成绩单。事情有没有做对，做对之后还要不要我从一堆废话里把关键决定翻出来，才是。

这些做法谈不上新发明，只是把 Julius 量过的那笔账，收成自己能执行的界限。笑话可以帮我记住「别啰嗦」。可当 Agent 开始连着干一天的活，真正要盯住的是另一句：它每一轮重新读进去的，是不是还必须在。

少说话不够。我更在意它每次重读了什么。
