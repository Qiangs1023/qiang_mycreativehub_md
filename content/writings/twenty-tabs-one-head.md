十一月八号，开发者 Sergey Kuhne 写了一篇文章，讲他怎么在 Claude Code 和 Codex 之间失去焦点的。文章在 Hacker News 上拿了九十多个赞、八十多条评论。他给这种状态起了个名字：AI brain fry，AI 烧脑。

他描述的过程我太熟了。开一个任务，模型要想一会儿，于是你另开一个填空。第一个回复来了，要澄清、要追问、还要顺手改个别的东西，每个都占一个标签。第二个回复又到了。跳着跳着，二十个线程，每一条的上下文都压在你脑子里。最后你不知道自己从哪开始，也不知道本来该在哪结束。

Kuhne 的诊断是两个问题：排序和上下文。解法是把所有活变成一张票据队列——每条是一个 markdown 文件，放在代码旁边，队列状态是 git 提交快照。Agent 按周期干活：研究新票据、做被标了「安全」的、跑测试和浏览器检查、验证已上线的东西；碰敏感代码就开分支先问，绝不直接部署。人只做一件事：脚本读整张队列，生成一份「所有者收件箱」，里面全是等你判断的事——审这个改动、答这个问题、裁决这个取舍。你打开一个页面，读完做了什么、为什么，给结论，结论写回 git。他说最关键的一步是「关闭」：拿起一项，装上它的上下文，做决定，写下来，然后放它回队列。这样它就不再挂在你的记忆里。他也很诚实：做这些还是累，但不再分心，不再迷路。

我信这套东西有效。它做的其实是一件很老的事：把状态从脑子里搬到纸面上。清单、番茄钟、各种待办方法论，都是这个动作的不同版式，git 只是让这张纸不会被一次崩溃弄丢。

但我读完第二天就发现，我并不同意它的一条潜台词。

HN 评论区有人替他挑明了：也许答案不是「把并行管理得更好」，而是「并行得少一点」。我看到这条时点了赞。队列解决的是「状态放哪」，没解决「你为什么要开第二个标签」。后者不是管理问题。二十个活之所以存在，是因为我在第一个活等回复的那九十秒里，受不了空着。

等待时开新任务，经常被说成是效率。我自己的体会是，它更像不安。模型在转，我的手闲着，闲着就显得慢。开源圈里这个压力更明显：别人仓库里挂着十来个进行中的改动，你只有一个，就会觉得自己在掉队。于是再开一个。不是第一个活真的堵住了，是我不敢让它安静地跑完。

去年我同时推三条线：开发、写作、还有一门课的讲义。我用上了能想到的所有工具——看板、自动化、每日复盘。工具确实一年比一年好用，我的线也一年比一年多。后来想明白这不是巧合：管理能力的提升，会把「我能不能同时干这么多」这个问题，悄悄换成「我怎么把这么多干得更整齐」。问题被换掉了，那个真正的答案就永远不会出现。我的实际限制一直没变——一次只能想一件事。这一条不随工具升级。

在课上我也见过同样的东西。学生开着课件、聊天窗、搜索、笔记，四五个窗口来回切。他们不是在多任务，是被多任务。切换的成本看不见，因为它不出现在任何一份成绩单上——没有人会因为「今天被打断了十四次」被扣分。但那段时间确实没了，用的是最贵的那部分：把一个想法想到底的耐力。

所以我现在给自己立了一条比 Kuhne 那套更笨的规矩：同时最多开两个线程。第二个必须是不需要判断的事——整理文件、回邮件、贴发票。任何需要我拿主意的活，不许在等待的空档里插进来。想插的时候，多半说明我在躲第一个活里最难的那一段。

第二条规矩更简单：队列里躺过三天没动的项，直接删，不重排优先级。一件真正重要的事，三天不动，要么它没那么重要，要么我在骗自己「回头会做」。重排只是让它继续躺着，而且躺得更体面。

我不打算把 Kuhne 的系统整个搬过来，我的工作量还配不上一张 git 票据板。但我会抄他那一步「关闭」：一件事判完，把结论写下来，然后让它从脑子里出去。这个动作不需要任何工具，一张纸也行。

二十个标签页不是工作流，是一个人在给自己找事。真正的解法不是把它们排好队，是让它们变成五个。
